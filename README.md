# Merchant MAXX

### Conversational AI commerce with deterministic checkout, safety guardrails, and real payment execution.

[![Backend Tests](https://github.com/divy-jn/merchant-maxx/actions/workflows/backend-tests.yml/badge.svg)](https://github.com/divy-jn/merchant-maxx/actions/workflows/backend-tests.yml)

Merchant MAXX is an AI-native e-commerce application that turns natural-language shopping intent into a real, bounded commerce transaction.

A customer can discover products, refine options conversationally, select quantities, manage a basket, pass through deterministic safety checks, confirm the purchase, and initiate a Razorpay checkout — without exposing internal tool state or identifiers in the customer experience.

The important design choice is that the LLM handles **intent and conversation**, while the backend remains authoritative for **inventory, prices, cart state, transaction limits, confirmation, and payment state**.

---

## Why MAXX

Traditional storefronts make customers translate intent into clicks. MAXX lets the customer describe what they want and keeps the interaction conversational all the way to checkout.

The system is designed around five principles:

- **Conversational discovery** — broad requests become useful shortlists instead of catalog dumps.
- **Deterministic commerce** — money-moving state is validated and mutated by backend tools and database state, not generated by the model.
- **Safe autonomy** — Guardian rules can block a transaction before payment and explain the block in customer-safe language.
- **Context-aware selection** — references such as “those 2” can resolve against the current conversation and basket context.
- **Recoverable payments** — payment and order transitions include idempotency and recovery paths for partial failures.

   ├───────────────┬───────────────┬───────────────┐
   ▼               ▼               ▼               ▼

MAXX also exposes ACP protocol/discovery routes from the backend for agentic-commerce interoperability.

## End-to-End Commerce Flow

```text
Natural-language intent
        ↓
Product discovery
        ↓
Conversational refinement
        ↓
Product / quantity selection
        ↓
Basket mutation
        ↓
Authoritative price + inventory validation
        ↓
Guardian safety evaluation
        ↓
Explicit customer confirmation
        ↓
Razorpay order / checkout
        ↓
Payment + order finalization
        ↓
Recovery path on partial failure
```

Example interaction:

> “Do you have a 2TB SSD?”
>
> “Show me other options.”
>
> “Give me those 2.”
>
> “Add another SSD.”
>
> “Make it 1.”
>
> “Proceed.”

The application keeps the product reference and quantity semantics tied to the current conversation rather than asking the model to invent or manipulate raw database identifiers.

## Safety and Transaction Guarantees

### Guardian: bounded commerce

MAXX does not treat an LLM approval as a payment authorization. Before checkout, authoritative server-side state is checked against configured commerce policies.

The production configuration includes a maximum transaction limit of **₹10,000** and requires explicit customer confirmation before payment.

A blocked purchase is translated into a customer-safe explanation instead of exposing internal rule identifiers or implementation details.

### Deterministic money path

The payment path is intentionally separated from natural-language generation:

- Cart totals are calculated from authoritative product data.
- Inventory and purchase state are checked server-side.
- Confirmation is handled through deterministic action paths.
- Razorpay identifiers are not surfaced as raw internal IDs in normal customer chat.
- Payment and order transitions are guarded against duplicate execution.

### Recovery

The backend includes payment/order recovery logic for partial failures, including webhook-driven recovery when a payment succeeds but the normal frontend completion path does not.

## Authentication

New customers can create an account from the application and then continue into the shopping experience.

The backend uses Supabase-backed customer state and enforces ownership around commerce resources. Guest conversation state can be claimed through the supported backend flow.

## Getting Started

### Prerequisites

- Python 3.11+
- Node.js / npm
- A Supabase project
- A Pinecone API key
- An LLM API key for the provider you configure
- Razorpay test credentials for payment flows

### 1. Configure environment

Create a local `.env` from the example file and fill in the required values.

```bash
cp .env.example .env
```

Never commit real API keys or service credentials.

### 2. Start the backend

```bash
cd backend
python -m pip install -r requirements.txt
python main.py
```

The FastAPI application exposes the API and commerce routes.

### 3. Start the frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

The frontend reads `VITE_API_URL` when configured; otherwise the local development configuration points to the local backend.

## Testing

Backend tests run with `APP_ENV=test` so the suite can validate application logic without accidentally triggering live LLM behavior.

```bash
cd backend
APP_ENV=test python -m pytest tests/ -v
```

The same backend test suite is executed in GitHub Actions for pushes to `main` and pull requests targeting `main`.

## Deployment

### Frontend

The frontend is deployed through Vercel.

### Backend

The backend is containerized and deployed to Google Cloud Run through `cloudbuild.yaml`.

The pipeline explicitly:

1. builds the backend image,
2. pushes the image to Google Container Registry,
3. deploys that image to the `merchant-maxx-api` Cloud Run service.

This keeps the deployed revision tied to the source commit used by Cloud Build.

## Security Model

MAXX treats the model as an untrusted decision-support layer around a trusted commerce core.

**Authoritative state lives in the backend.** Product prices, inventory, cart contents, customer ownership, purchase state, transaction limits, and payment state are not accepted from free-form model output.

**RLS protects customer data.** Supabase Row Level Security is used to constrain customer access to commerce records, while server-side service credentials are kept for trusted backend/webhook operations.

**Customer output is sanitized.** Internal product IDs, recommendation IDs, purchase/order identifiers, and Guardian implementation details are removed or translated before customer-facing responses are returned.

See [`docs/SECURITY.md`](docs/SECURITY.md) for the deeper security model.

## What Makes the Architecture Different

A conversational shopping agent is only useful when it can safely cross the boundary from text to money.

MAXX makes that boundary explicit:

```text
LLM
 └─ understands intent / produces conversational responses

Backend tools + database
 └─ decide what is actually true

Guardian + confirmation
 └─ decide whether the transaction may proceed

Razorpay
 └─ executes the payment
```

This separation is what lets MAXX support an agentic UX without giving the language model authority over financial state.
